//* winkey+LMB drag started while the Windows Start Menu is already open: the window would visibly lag behind the cursor then "snap" forward, and if the cursor drifted over a different window mid-drag it would suddenly start dragging THAT window instead; releasing winkey afterward would also close the still-open Start Menu instead of leaving our Start-menu-suppression tap to handle it, and one subsequent bare winkey tap would do nothing while the tap after that would open the menu again. Resize (winkey+RMB) was never affected. Root cause: with Start Menu open, forceForeground/SetForegroundWindow reliably fails to steal focus away from it (a long-documented, expected failure mode -- see forceForeground's own doc comment), and in that specific state a second, spurious WM_LBUTTONDOWN for the very same physical click can arrive while our drag is already in progress (most likely the shell's own click-outside-to-dismiss-Start-Menu handling replaying/re-delivering the click; low-level mouse hooks are always called in chain order regardless of an earlier hook's swallow, so the shell's own hook logic still sees the original click even though we returned 1 for it). tryBeginMoveGestureAt's existing "always tear down and restart the drag on any LMB-down, even for the same window" logic (added earlier for a different, legitimate reason -- see its own doc comment) then treated that spurious duplicate exactly like a fresh click: it re-baselined the drag against a GetWindowRect that can be visually stale (this exact drag can already have SetWindowPos calls queued in moveDataChan that the main thread hasn't drained/applied yet -- see handleActualMoveOrResize) and re-resolved the target window via WindowFromPoint at that moment, silently retargeting onto whatever window the cursor had since drifted over. Fixed by adding isSpuriousDuplicateButtonDown(), checked as the very first thing in mouseProc's WM_LBUTTONDOWN/WM_RBUTTONDOWN/WM_MBUTTONDOWN handlers: if lmbDownSwallowed/rmbDownSwallowed/mmbDownSwallowed is already true for that exact button (meaning we already ate a down for it with no matching up seen yet -- something real hardware can never do on its own), the event is re-swallowed and otherwise completely ignored, leaving whatever gesture is already in progress untouched. Applied symmetrically to RMB and MMB too even though only LMB/Move was ever observed affected, since MMB's one-shot send-to-back/restore action could otherwise double-fire on the same kind of duplicate down.
//* follow-up to the winkey+LMB-drag-while-Start-Menu-is-open entry above: ignoring the spurious duplicate WM_LBUTTONDOWN alone was NOT sufficient -- the drag would still move a little (or, if the user was slow, not at all) and then abruptly stop while LMB and winkey were both still physically held. Root cause traced one level deeper: with the Start Menu open, forceForeground fails (as already documented), so WM_FOCUS_TARGET_WINDOW_SOMEHOW's handler falls back to injectLMBClickAtCoords -- a REAL, injected LMB down+up via SendInput at the drag's start coordinates. The Start Menu's own click-outside-to-dismiss handling intercepts that injected click, dismisses itself, and -- following the ordinary Windows popup convention that a dismissing click also passes through to whatever's beneath it -- redelivers a fresh, UNMARKED WM_LBUTTONDOWN+WM_LBUTTONUP pair at that location (unmarked because it's the shell's own SendInput, not tagged with ourInputExtraInfoMarker, so mouseProc treats it as ordinary physical input). The replayed down was already being safely ignored by the isSpuriousDuplicateButtonDown fix above, but the replayed up right after it was not: mouseProc's WM_LBUTTONUP handling unconditionally ends an active ModeMove session on ANY up for that button (by design, so a genuinely missed matching down doesn't leave a session stuck forever), so that one injected click was silently killing the user's still-active drag. Resize was never affected because this fallback only ever injects an LMB click regardless of which button started the gesture, and a ModeResize session is RMB-tracked, so the replayed LMB-up never matched WM_LBUTTONUP's own mode==ModeMove check. Fixed at the actual source: injectLMBClickAtCoords now refuses to inject anything at all while isAnyGestureActive() (any Move or Resize session currently in progress, regardless of which window either targets) -- since WM_FOCUS_TARGET_WINDOW_SOMEHOW is only ever posted right as a gesture starts, this means the fallback essentially never fires for its one real use case anymore, trading away auto-focusing the dragged window specifically during the Start-Menu-open edge case in exchange for never injecting a real click onto a window the user is actively dragging/resizing (which was already independently unsafe regardless of the Start-Menu-replay mechanism -- see this function's older exit-button caveat).
